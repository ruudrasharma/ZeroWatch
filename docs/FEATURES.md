# Features — ZeroWatch (feature-by-feature behavior spec)

## Recon Engine

### SSL/TLS analysis
- Checks certificate validity dates, issuer, protocol versions supported (flags TLS 1.0/1.1 as findings), cipher suite strength.
- Severity: expired/self-signed cert → critical; weak cipher/old protocol supported → medium; all clear → informational pass shown in report.

### Security header audit
- Checks presence/correctness of: `Content-Security-Policy`, `Strict-Transport-Security`, `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`.
- Each missing header is its own finding, severity pre-assigned per header (e.g. missing CSP = high, missing Referrer-Policy = low).

### Cookie security
- Inspects `Set-Cookie` headers for `Secure`, `HttpOnly`, `SameSite` flags.
- Missing `Secure` on a cookie set over HTTPS = high; missing `HttpOnly` on a session-looking cookie = high; missing `SameSite` = medium.

### Tech fingerprinting
- Detects CMS/framework/JS libraries and versions from response headers, meta tags, and known JS file signatures (Wappalyzer-style heuristic matching).
- Output feeds directly into CVE cross-reference step.

### CVE cross-reference
- For each fingerprinted technology + version, queries NVD CVE API for known vulnerabilities.
- Findings include CVE ID, CVSS score (used to set severity), and a plain-English summary generated by the local LLM.

### Exposed path detection
- Checks a curated list of common sensitive paths (`.env`, `.git/config`, `/wp-config.php.bak`, `/admin`, `/.aws/credentials`, etc.) for accessibility (HTTP 200 response).
- Any accessible sensitive path = critical finding.

### Subdomain/DNS checks
- Queries crt.sh for certificate transparency records to enumerate subdomains.
- Flags subdomains that resolve but appear to host outdated/unmaintained services (best-effort heuristic, disclosed as such).

### Risk score
- Weighted composite: critical findings weighted heaviest, informational passes reduce score toward 0. Exact formula documented in code comments (`backend/services/scoring.py`) and kept in sync here.

### AI report generation
- All findings assembled into structured JSON, sent to local Ollama LLM with a fixed prompt template requesting: plain-English explanation, why it matters, concrete remediation step. Output is stored per-finding, not regenerated on every view (cached in `findings.remediation`).

## Zero-Day Anomaly Engine

### Dataset replay
- Pre-processed CICIDS2017/2018 flow records replayed over WebSocket at a configurable pace (default: simulate real-time inter-arrival spacing, capped for demo watchability).

### Model scoring
- **Autoencoder**: reconstruction error on the flow's feature vector = anomaly score, normalized 0–1.
- **Isolation Forest**: path-length-based anomaly score, normalized 0–1.
- **Random Forest baseline**: supervised classifier, predicted probability of "attack" class used as comparison score (not a true zero-day detector, included explicitly as the contrast case).

### Leave-one-attack-out evaluation
- For each held-out category, the model is trained/evaluated with that category fully excluded from training data, then tested on a mixed set including the held-out category.
- Metrics computed: precision, recall, F1, false positive rate — stored in `model_evaluations` table.

### SHAP explainability
- Computed only for flagged instances (not the full stream, for performance).
- Top 5 contributing features returned per alert, rendered as a horizontal bar chart.

### Threshold tuning
- Slider adjusts the score cutoff for "flagged" classification live during replay; precision/recall preview (computed against already-seen flows in the current run) updates as the slider moves.

### Signature comparison
- Each flow is also checked against a small hardcoded set of known Snort-style signatures (for demo purposes — a handful of real, publicly documented rules).
- Alert detail explicitly shows "Signature match: none" for genuinely novel-category flows, reinforcing the zero-day narrative.

### Severity bucketing
- Anomaly score mapped to severity: `<0.5` not flagged, `0.5–0.7` low, `0.7–0.85` medium, `0.85–0.95` high, `>0.95` critical (defaults, adjustable in code).

## Platform features

### Dashboard
- Aggregates counts from `scans` and `detection_runs`/`alerts` tables; recent activity feed pulls last 5 records across both, sorted by timestamp.

### History
- Read-only view over `scans` and `detection_runs`, joined with their child records for detail drill-down.

### PDF export
- Server-side rendering of the same report data used in the web view, styled via a dedicated PDF template (WeasyPrint/reportlab), triggered on-demand (not pre-generated).

### Theme toggle
- Persisted in browser localStorage; no backend involvement.
